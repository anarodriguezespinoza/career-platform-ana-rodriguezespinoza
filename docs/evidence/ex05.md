# Exercise 05 — DNS Investigation

## Setting and prediction

For this assignment, I used the simulation provided and interpreted the components and outcome.

For the setup, the `site.lab.example` should reach a new Railway deployment, where Cloudflare is the DNS provider for lab.example, and the record is DNS only, so Cloudflare does not proxy it or terminate TLS. The Railway URL already serves the current page and database content, so the app itself works.

**Failed check:** `dig site.lab.example A` followed by `curl -Iv https://site.lab.example/`.

**Prediction:** `dig` should show `site.lab.example` as a CNAME to `current-app.up.railway.app`, followed by Railway's addresses. `curl` should connect to a Railway IP, get a certificate valid for `site.lab.example`, and return an HTTP `200` with the same page the Railway URL returns.

## Failed check and evidence

Date: 2026-10-13

**simulated:**
```text
$ dig site.lab.example A +noall +answer
site.lab.example.  300  IN  A  198.51.100.24

$ curl -Iv https://site.lab.example/
* Connected to site.lab.example (198.51.100.24) port 443
* Server certificate: subject: CN=old-vm.lab.example
* SSL: certificate subject name does not match target host name 'site.lab.example'
curl: (60) SSL certificate problem: certificate subject name does not match target host name
```

What actually happened compared to what I predicted:

The DNS gave back an A record pointing to 198.51.100.24, the old Azure VM and there was no CNAME to Railway. The`curl` connected to that old IP on port 443, so something is still listening there and the certificate it got was for `CN=old-vm.lab.example`, not `site.lab.example`, so curl stopped with error 60 before any HTTP request was sent, which means no HTTP status came back.

## Diagnosis

The name resolves to the wrong place. The zone still has the old Azure A record, so clients never reach Railway at all. This is the first fault, and the `dig` answer supports it directly as the address is not a Railway address, and there's no `current-app.up.railway.app` CNAME. There was a TLS certificate error but it comes from the DNS failure, since curl reached the old VM, it got that VM's certificate. That certificate was never issued for `site.lab.example`, so the name check fails and the `Connected to ... (198.51.100.24)` line ties the TLS failure to the address that came from DNS.

In Cloudflare, I need to delete the `A site → 198.51.100.24` record and add `CNAME site → current-app.up.railway.app`, and keep DNS only. They have to be swapped because a name can't have a CNAME alongside another record. The ownership TXT is already verified, so once Railway sees the CNAME it should issue its own certificate for `site.lab.example`.

What's still uncertain:
- Resolvers may keep giving the old A record for up to the 300-second TTL after the change.
- Railway may need a few minutes to issue the certificate. During that time the DNS could be correct while TLS still fails, which would be a separate problem.
- Even if DNS and TLS both work, that doesn't prove the custom domain serves the right page and database content. I'd still need to check the HTTP response.
- The old VM is still answering on 443. After the cutover it should be shut down or cleaned up.

## Repair and repeated check

To repair the failure, I would replace `A site.lab.example → 198.51.100.24` with `CNAME site.lab.example → current-app.up.railway.app`.

**Repeated check (simulated follow-up):** 
```text
$ dig site.lab.example A +noall +answer
site.lab.example.  300  IN  CNAME  current-app.up.railway.app.
current-app.up.railway.app.  300  IN  A  203.0.113.44

$ curl -Iv https://site.lab.example/
* Connected to site.lab.example (203.0.113.44) port 443
* Server certificate: subject: CN=site.lab.example
* SSL certificate verify ok.
< HTTP/2 200
```

Comparison with my first check:

| | Before (simulated) | After (simulated) |
|---|---|---|
| DNS answer | `A 198.51.100.24` | `CNAME current-app.up.railway.app.` → `A 203.0.113.44` |
| Connected address | `198.51.100.24` (old Azure VM) | `203.0.113.44` (Railway) |
| Certificate name | `CN=old-vm.lab.example` (mismatch) | `CN=site.lab.example` (verify ok) |
| HTTP result | none (curl error 60) | `HTTP/2 200` |

The old `A site.lab.example → 198.51.100.24` record is gone. It was replaced by `CNAME site.lab.example → current-app.up.railway.app`, which resolves to Railway's address `203.0.113.44`.

The follow-up matches the repair I proposed. Once the name pointed to Railway, curl connected to a different address, got a certificate issued for `site.lab.example`, and got a `200`. This shows the wrong DNS record was the fault that came first. The certificate mismatch only happened because DNS sent curl to the old VM. Nothing was wrong with Railway's certificate.

However, `curl -I` only asked for headers, so a `200` shows the page responds but doesn't prove it shows the current page and database content. I'd still need to load the page and compare it with the Railway URL. In a real cutover, other resolvers could still give the old A record until the 300-second TTL runs out.

## What I learned

DNS alone doesn't prove HTTPS works, and a TLS error doesn't always mean the certificate is broken. In this case it meant I was talking to the wrong server.

One check that separates DNS from TLS or the app is to skip DNS and connect straight to the intended host while still sending the real name:

```text
curl -Iv --connect-to site.lab.example:443:current-app.up.railway.app:443 https://site.lab.example/
```

If that works, Railway's certificate and the app are fine and the problem is only DNS. If it still fails on the certificate, the problem is on the TLS or Railway side. If TLS works but the response is wrong, it's the app. Comparing `dig @1.1.1.1` with a query to Cloudflare would also show whether a wrong answer is a stale cached result or the actual record.

If the failure is still there after the repair, I would check next: whether cloudfare returns the CNAME, whether Railway's custom-domain page shows the certificate as issued, and whether `curl https://site.lab.example/` returns the same content as the Railway URL.
